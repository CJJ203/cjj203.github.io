    LLM 服务性能测试

    LLM 服务容量测试的目标，是找出每路响应速度达标时能够承受的并发路数，并明确这一并发对应的输入输出长度和资源开销。整机 tok/s 很高，并不意味着每个用户都足够快；短请求下通过的并发，也不一定适用于长上下文或长回答。 本文以单张 RTX 5090 上已经运行的 Qwen3-0.6B 为例，使用 sglang.bench_serving 的实现发送 OpenAI 兼容的 /v1/chat/completions 流式请求。按照测试目标、测试范围、测试方法、测试结论、报告出具五部分，给出并发边界、资源占用和长度劣化的实测结果。工具用法参见 SGLang 官方评测指南 与 中文指南。 1. 测试目标 1.1 找到满足单路响应标准的最大已验证并发 “一路”指一个持续请求的虚拟用户，任一时刻最多有一条 HTTP 请求在执行。客户端设置最大并发 C，请求完成后由后续任务补充，让服务在批次主体阶段维持约 C 条在途请求。本次每组至少 128 条请求、至少 6 轮并发请求，并重复 3 次。 先设置一套适用于交互演示的响应标准。它是本次测试采用的 SLO，不是行业统一要求；实际项目应根据用户体验确定。 验收项 本次标准 判定口径 单路生成速率 至少 50 token/s 逐条正式请求计算，所有成功请求均须满足，不能只看平均值或整机吞吐 首个输出等待 P99 TTFT ≤500 ms 每次运行分别判定 完整回答等待 P99 E2E ≤10 s 每次运行分别判定，约束长输出带来的总等待 生成期间卡顿 P99 ITL ≤100 ms 以当前客户端收到的非空流式内容块间隔统计 成功与稳定性 正式请求全部成功 无请求失败、超时或服务重启；未观察到 OOM 类错误，资源采样完整 首个输出后的单路生成速率定义为： $$ R_i=\frac{L_{\mathrm{out},i}-1}{T_{\mathrm{E2E},i}-T_{\mathrm{TTFT},i}} \quad\mathrm{token/s} $$时间使用秒。R_i ≥50 token/s 等价于该请求的 TPOT ≤20 ms/token。它衡量开始输出后的平均生成速度；首个输出等待与完整回答时间另由 TTFT、E2E 限制。逐请求速率要求全部达标，而 TTFT/E2E 使用 P99，不能把两种口径混为“每条请求的所有延迟都不超限”。 ...

    训练一个大语言模型，到底要算多少？从 6ND 说起

    假设手里有一批 GPU，准备训练一个 7B 模型。最先冒出来的问题往往很直接：这些卡够不够？要跑多久？把上下文从 2K 拉到 8K，会贵多少？ 查资料时，很容易碰到一个简洁得有点让人不放心的公式： $$ C \approx 6ND $$参数量乘上 token 数，再乘以 6，就能估算训练计算量。一个那么复杂的 Transformer，真能这么算？ 这个公式确实有用。不过，要把它变成可靠的训练预算，还得知道那个 6 从哪来、它省略了什么，以及算出来的数字如何换成天数。 本文以 Adam Casson 的 Transformer FLOPs 为计算量部分的线索，结合 Jianbin Chang 的 GPT Training Memory Estimation — NeMo Practice 讨论显存约束。下面主要考虑稠密、decoder-only Transformer 的全参数训练；MoE、参数高效微调和推理需要另算。 先把三个容易混在一起的量分开 估算训练资源时，我们实际上在问三个问题： 量 回答的问题 常见单位 计算量 FLOPs 总共要做多少次浮点运算？ FLOPs、PFLOPs 算力 FLOP/s 每秒能完成多少次浮点运算？ TFLOP/s、PFLOP/s 显存 训练过程中要同时存下多少东西？ GB、GiB 可以把它们想成做饭：计算量是要处理多少食材，算力是处理食材的速度，显存是操作台有多大。操作台不够，得分批处理，或者把一些东西临时挪走；这些安排又会影响速度。 这也解释了为什么“模型权重能放进显存”和“模型能训练起来”之间，还有很长一段距离。 那个 6，是从矩阵乘法里来的 先看一个普通的线性层： $$ Y=XW $$假设输入有 $T$ 个 token，$X$ 的形状是 $T\times h$，权重 $W$ 的形状是 $h\times k$。矩阵乘法的主要计算量约为： ...
